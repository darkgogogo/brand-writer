# brand-writer-check 四层自检 skill

> 本 skill 依赖 `~/.claude/skills/brand-writer/references/constants.md` 的共享常量（stage 枚举、路径规则）。

灵感源自软件测试金字塔：L1 自动扫描 → L2 单元测试 → L3 集成测试 → L4 人工终审。
**V2 新增**：L4 过关后不自动 chain，必须等人工审阅标记（D1）。

## 输入

- 文章路径（例：`$BRAND_WRITER_HOME/articles/XXX/XXX.md`）
- Session 路径（同目录 `_session.json`）→ 读取 `style_source`、`blogger`、`blogger_report_path`、`borrowed`、`archetype`、`hkr`
- 禁用词清单：`references/banned-words.md` + 博主专属（动态加载） + profile 豁免词（可选）
- 对话开头用户表达的写作目标（用于 L4 目标对齐）

## L0 HKR 复核（选题质检回读）

读 `_session.json.hkr`：
- 字段不存在或为 null → L0 section 输出 `⚠️ 未检测到 HKR 记录，write-article 没跑选题质检` + 继续 L1（不阻塞）
- `pass == false` → L4 活人感终审时额外补一句 `⚠️ HKR 判定未过（notes: <原因>），建议跟用户确认是否返工`
- `pass == true` → 正常继续，L0 输出 `✅ HKR 通过（H/K/R: <勾选详情>）`

## L1 硬性规则扫描（两层机制：Layer A 预处理 + Layer B 三级匹配）

### Layer A — 引用自动豁免预处理

扫描正文前，先构造"清洗版本"：
1. 剔除 `^>` 开头的 blockquote 行（引用博主原话、用户原话常用此格式）
2. 剔除 ` ``` ` 包裹的多行代码块
3. 剔除 `` ` `` 包裹的行内代码
4. 剔除 YAML frontmatter（`---` 之间）

L1 只在清洗版本上做词表匹配。被豁免的引用段单独统计，仅在 🟢 section 记录行号。

### Layer B — 词表三级匹配

从 `references/banned-words.md` 加载三级词表：
- 🔴 第一级强禁 + 博主专属禁用（动态，来自 `style-reports/<platform>/<博主>.md` 的「禁用词清单」section） → 必改
- 🟡 第二级条件禁 → 请复核
- 🟢 第三级弱禁 → 提示

**profile 豁免词合并（D14）**：加载当前产品的 profile（例 `~/.claude/skills/brand-writer/profiles/example-product.md`），如果存在 `## 豁免词` section，则：
1. 解析该 section 下的词条（每行 `- <词>：<豁免理由>` 格式，详见 `references/banned-words.md` 格式示例）
2. 在匹配前从 🔴/🟡/🟢 词表里**剔除**这些词（只对本产品生效，不改全局文件）
3. 在 L1 section 末尾追加一行：`> 本次自检已豁免 profile 登记词：X 个（来自 example-product profile）`

若 profile 无 `## 豁免词` section → 正常全量匹配，不做任何处理。

**风格源决定扫描等级**（结合 constants.md 的风格源枚举）：

| 风格源 | 扫描等级 |
|---|---|
| `official` | 🔴 全量 + 🟡 全量 + 🟢 频次统计 |
| `mimic_blogger` | 🔴 全量 + 博主专属禁用合并 🔴 + 🟡 严格版（提示频次 <1 次/篇）+ 🟢 统计 |
| `free` | 仅 🔴 全量 + 🟢 统计 |

### 输出分栏

L1 section 按三级分栏写入 self-check-report.md：

```markdown
## L1 硬性规则扫描

### 🔴 必改（强禁 + 博主专属）
- L42 命中 "毋庸置疑" → 建议改为"显然"或删除
- L87 命中 "从技术到用户体验" → 建议改写

### 🟡 请复核（条件禁）
- L15 出现 "精准"。当前语境是产品描述，可保留但注意频次。

### 🟢 提示（弱禁 + 引用豁免）
- "非常" 全文出现 6 次（阈值 5），建议降频
- 已跳过扫描的 blockquote：L10, L23, L45
```

**阻塞规则**：🔴 必改未清零 → L2 不开工。🟡/🟢 不阻塞。

### Layer C — 结构完整性检查

除词表匹配外，L1 还会扫正文中的配图标注（下游 `brand-writer-image` 依赖）：

- 统计正文区（`## 正文` 到 `## English Version` 之间）内 `📷 **配图建议**` 的出现次数 `N`
- 统计正文字数 `W`（去掉 markdown 语法、配图标注行、空白后的纯中文字符数）
- 按字数动态推导期望 `E = round(W / 500)`（对应 write-article 的"1500 字 3-4 张，每 ±500 字 ±1 张"规则）

**判定（按 |N - E| 容差）**：

| 条件 | 级别 | 行为 |
|---|---|---|
| `N == 0` | 🔴 强禁 | 计入 L1 必改，L2 不开工（硬规则，不看字数） |
| `|N - E| ≤ 1` | ✅ | 通过（例：1500 字时 N ∈ [2, 4]、2000 字时 N ∈ [3, 5] 都 ✅） |
| `|N - E| == 2` | 🟡 条件禁 | 偏少则提示补齐，偏多则提示合并 |
| `|N - E| > 2` | 🔴 强禁 | 密度严重失衡，L2 不开工 |

**示例**：

| W 正文字数 | E 期望张数 | ✅ 范围 | 🟡 范围 | 🔴 范围 |
|---|---|---|---|---|
| 1000 | 2 | [1, 3] | 4 | 0 / ≥5 |
| 1500 | 3 | [2, 4] | 1/5 | 0 / ≥6 |
| 2000 | 4 | [3, 5] | 2/6 | 0-1 / ≥7 |
| 2500 | 5 | [4, 6] | 3/7 | 0-2 / ≥8 |

**附加检查**（仅当 `N > 0`）：格式必须精确匹配 `📷 **配图建议**（AI生成/设计师制作）：...`。不合格格式计入 🟡 请复核：

- 描述字数 < 15 字（太空泛）→ 🟡
- 描述含风格词（"插画"/"手绘"/"写实"等）→ 🟡（风格由 generate-images 控制）
- 缺 "（AI生成/设计师制作）" 后缀 → 🟡

Layer C 的结果**合并进 L1 section 的 🔴/🟡/🟢 三级分栏**（与 Layer B 的词表匹配共用同一个输出区，不单独开 section）——按本 section 顶部的 E/N 判定表执行：`N==0` 或 `|N-E|>2` 写到 🔴；`|N-E|==2` 或附加检查不合格写到 🟡；`|N-E|≤1` 不输出。

## L2 风格一致性检查

读 `_session.json` 的 `style_source` 和 `borrowed` 列表。

**借鉴维度不判定为偏离**（D6 核心约束）：
- 若 `borrowed` 含 `(差评, title)` → 5 个标题候选按差评风格评估，而非主风格
- 若 `borrowed` 含 `(槽值, opening)` → 开篇按槽值风格评估
- 其他维度仍按主风格源评估

逐项给出"✅/❌"判断：

### 开头（L2-1）
- 是否从具体、当下的事件/场景切入（不是宏大叙事）
- 第一句话是否让读者产生"然后呢？"的冲动
- 有没有用任何教科书式开头
- 若 `borrowed` 含 `opening` → 按借鉴博主的开篇风格判定

### 节奏与结构（L2-2）
- 长短句交替？（连续 3 句以上相近长度 = 节奏呆板）
- 至少 3 次一句话独立成段的"断裂"效果
- 偏离主线段落后有"扣主线句"拉回来
- 有用疑问句做节奏的"刹车和转向"
- 避免不必要的小标题（模仿博主时；官方调性可以有小标题）
- 若 `borrowed` 含 `pacing` → 按借鉴博主的节奏判定
- 若 `borrowed` 含 `ending` → 结尾段按借鉴博主的收尾风格判定

### 口语化（L2-3）
- 使用了风格源推荐的词组
  - 官方调性：至少 3 个产品档案「写作偏好」的词
  - 模仿博主：至少 8-10 个 style-report「推荐词组清单」的词
  - 自由写：不要求
- 若 `borrowed` 含 `interaction` → 互动密度按借鉴博主的要求
- 论述中有"故意打破"（重复强调、中途打断、省略主语）
- 至少一处自嘲或承认不足
- 标点用来表达情绪（"。。。" "？？？" "= ="）

### 标点禁令二次确认（L2-4）
- AI 容易在修改过程中重新引入禁用标点，再扫一遍
- 模仿博主时特别检查：破折号 / 英文双引号 / 不必要小标题

**L2 通过标准**：L2-1 全部通过，L2-2 至少 3/4，L2-3 至少 3/4（按风格源），L2-4 通过。

## L3 内容质量检查

### 观点支撑（L3-1）
- 每个核心观点都有具体的人/场景/细节/数据支撑
- 没有空泛论断（"AI 正在改变一切"）

### 知识输出方式（L3-2）
- 知识点是"聊着聊着顺手掏出来"
- 没有教科书式科普（"下面我来介绍"）
- 引用（论文、书、历史）自然融入

### 文化升维（L3-3，可选）

**触发条件**（满足任一即检查，否则跳过本维度）：
- `archetype ∈ {phenomenon, investigation}`（现象解读 / 调查实验天然需要升维收尾）
- `style_source == "mimic_blogger"` 且博主风格报告 `style-reports/<platform>/<博主>.md` 的「文化升维倾向」字段值为 `high`

**检查项**：
- 有至少一处从具体事件连接到更大文化/哲学/历史参照物
- 连接自然，不是硬凑

### 对立面与同理心（L3-4）
- 讲核心观点时，有对对方立场的理解和承认
- 先站到读者处境里，再给出自己视角

### 文章类型专项（L3-5）
根据 `archetype` 做针对性检查：
- `trouble_shoot` → 是否含 profile「联系方式」section 中的客服邮箱？每步操作是否能跑通？
- `pitfall` → 每条高危是否带具体场景？善后方案是否实用？
- `science` → 是否从用户感受切入（不从品牌视角开篇）？类比是否贴近日常？
- `investigation` → "亲自下场"感是否强？有无逐一展示 + 升番逻辑？
- `experience` → "跟我一起玩"感？感受是否具体？
- `phenomenon` → "观察→好奇→研究→升维"推进？升维是否自然？
- `free` → 仅跑 L3-1/L3-2/L3-4，跳过结构专项

### 逐一展示（L3-6）
- 如涉及多个产品/案例比较，用了逐一展示（每个带吐槽点评）而不是一次性罗列

**L3 通过标准**：L3-1 和 L3-2 必须全部通过；L3-3 到 L3-6 按文章类型相关项通过。

## L4 目标对齐 + 活人感终审

### L4-1 目标对齐

对照对话开头用户表达的写作目标：
- 用户提出的每一个核心诉求，是否在文章中有对应体现？
- 文章整体方向是否与用户希望读者产生的感受/行动一致？
- 有无遗漏的叙事线或必须覆盖的内容点？
- 品牌露出分寸是否符合用户预期？

如有遗漏或偏差，在修复优先级里标注。

### L4-2 活人感终审

通读全文，回答核心问题：
> 读完这篇，感觉是一个有见识的普通人在认真聊一件打动他的事，还是一个 AI 在给我输出信息？

维度：
- **温度感**：情绪表达是体感记忆（"我当时就愣住了"）还是知识性描述（"我感到非常震撼"）？
- **独特性**：这篇有"只有这个视角才能写出来的角度"吗？
- **姿态检查**：语气是不是"有见识的普通人在聊打动他的事"？
- **心流检查**：从头到尾读，哪里注意力断掉了？

**L4 通过标准**：整体感觉"像真人写的"。任何一项让你觉得"这段 AI 味太重了"就要返工。

## 输出格式（V2 变更，D2）

**独立文件**：所有自检内容写入 `articles/<标题>/self-check-report.md`，**不**追加到主 `<标题>.md`。

文件结构（详细模板见 `references/checklist-template.md`）：

```markdown

[✅ 通过 / ⚠️ 未过（含 notes） / ⚠️ 未检测到]

## L1 硬性规则扫描
[三级分栏输出]

## L2 风格一致性
[主风格匹配 + 借鉴维度说明]

## L3 内容质量
[...]

## L4 目标对齐 + 活人感
[...]

```

生成后：
1. 更新 `_session.json` 的 `stage` 为 `human_review_pending`
2. **不**自动 chain 到 social 或 image
3. 告诉用户：
   > ✅ 4 层自检已全部通过。请打开 `self-check-report.md` 人工审阅。
   > 通过后告诉我 **"审阅通过"**，我才会继续后续步骤（社媒/配图）。

## 人工审阅 gate（V2 新增，D1）

**设计**：分布式。self-check 只负责**写标记**和**停机**；下游 skill（brand-writer-social / brand-writer-image）各自在启动时**自己读** `self-check-report.md` 判断是否通过。

### 等待期（self-check 的唯一职责）
4 层全通过后：
1. 更新 `_session.json.stage` = `human_review_pending`
2. self-check 流程到此为止 — 不自动 chain 下游，也不"拒绝"任何调用（拒绝由下游自己判定）

### 通过信号
用户说"审阅通过"、"审了 OK"、"pass"等等效表达 → 执行：
1. 在 `self-check-report.md` 末尾追加：
   ```markdown
   **人工审阅**：✅ 通过 @ <YYYY-MM-DD HH:MM>
   ```
2. 更新 `_session.json.stage`：清除 `human_review_pending`，设为 `idle`
3. 告诉用户下一步建议：
   > 审阅已记录 ✅。接下来可以：
   > - 生成社媒文案（brand-writer-social）
   > - 生成配图（brand-writer-image）
   > - 修改某段后重跑自检
   > - 就到这了

### 下游 skill 如何检查（说明，非本 skill 职责）
下游 skill 启动时自己读 `self-check-report.md` 末尾：
- 末尾有 `**人工审阅**：✅ 通过 @ ...` 行 → 放行
- 无该行 → 拒绝执行并提示用户"请先人工审阅 self-check-report.md"

## 边界

- 只做自检输出，不自动修改文章（修改建议给用户，用户决定是否采纳）
- L4 通过 ≠ 流程结束：必须经人工审阅 gate 才能继续
- 如果某层严重不通过（L1 🔴 多处、L4 整体 AI 味重），在 self-check-report.md 开头加"⚠️ 强烈建议返工"
