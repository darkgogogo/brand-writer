# brand-writer-article 主写作 skill

> 本 skill 依赖 `~/.claude/skills/brand-writer/references/constants.md` 的共享常量定义（路径、stage 枚举、原型枚举等）。

## 前置条件

进入本 skill 前，需要以下上下文（由 brand-writer 准备好，或本 skill 自己收集）：
- 产品档案（`~/.claude/skills/brand-writer/profiles/<产品名>.md` 的全部内容）
- 风格源（`用官方调性写` / `模仿博主写` / `自由写`）
- 博主风格报告路径（仅在模仿博主时需要）
- 文章原型（故障排查 / 排雷避坑 / 产品科普 / 调查实验 / 产品体验 / 现象解读 / 自由）
- 局部借鉴 `borrowed`: `[{blogger, dimension, report_path}, ...]`（可空，V2 新增）

缺的项按顺序向用户问。

## 启动流程

### 1. 苏格拉底提问收集写作目标

每次只问一个问题，按重要性排序追问：
1. 本次文章的核心目标：希望读者看完产生什么感受或行动？
2. 目标读者是谁，他们现在的认知和情绪状态？
3. 涉及的技术背景或关键事实（可粘贴内部文档）
4. 是否需要联网搜索补充信息
5. 有无必须提到或绝对不能提的内容
6. 是否多篇联动（影响品牌露出梯度、发布顺序）

持续问到对"写什么 / 为什么写 / 给谁看 / 希望达到什么效果"有 95% 把握，主动告知"已充分了解"进入下一步。

### 1.5. 写入初始 _session.json（V2 新增，D8）

创建 `$BRAND_WRITER_HOME/articles/<标题>/_session.json`：

```json
{
  "article_title": "...",
  "product": "...",
  "profile_path": "...",
  "style_source": "...",
  "blogger": "...",
  "blogger_report_path": "...",
  "borrowed": [],
  "archetype": "...",
  "topic": "...",
  "stage": "drafting",
  "hkr": null,
  "created_at": "<ISO>",
  "updated_at": "<ISO>"
}
```

`hkr` 初始为 `null`，在 Step 2 HKR 质检完成后回填（格式见 Step 2）。正文开始写作时 `stage=drafting`，写完切换为 `self_check` 后再 chain 到 brand-writer-check。

### 2. HKR 选题质检

判断选题质量：

- **H (Happy)**：足够有趣、有悬念吗？标题和开头能让人好奇想点开吗？
- **K (Knowledge)**：有信息量吗？看完能学到新东西吗？
- **R (Resonance)**：能戳中情绪吗？让人"对对对我也这么想"？

S 级选题三项兼备，及格选题至少占两项。如果素材的选题方向明显只占一项或一项都没有，**主动跟用户沟通调整方向**，不强行开写。

如果素材信息不够（只有主题没具体要点），主动问："你大概想讲哪几个点？有没有什么自己的经历想放进去？有没有什么让你特别兴奋或者特别想吐槽的地方？"

**结果持久化**：判定后把结果写入同目录 `_session.json`：

```json
"hkr": {
  "h": true,
  "k": true,
  "r": false,
  "pass": true,          // true = 至少 2 项占，允许开写
  "notes": "K 没占，因为这事行业里没什么新知"
}
```

**字段要求**：
- `pass=false` 时 `notes` **必填**，需写明"为什么仍要开写"——这是给 self-check L4 复核和用户事后追溯的依据
- `pass=true` 但有维度未占时，`notes` 说明哪项没占、为什么可以接受（如示例）
- 三项全占且无保留时，`notes` 可为空字符串

self-check 会读 `hkr.pass` 复核；若 `pass=false` 但文章还是写出来了，self-check L4 会给出"建议返工"提醒。

### 3. 从业者素材收集（硬性 gate）

> 关键概念："AI/人边界"——针对品牌号场景的素材采集要求。**核心洞察**：AI 凭空想象的场景会显得很假；真正让文章立住的，是从业者（用户本人 + 同事 + 一线渠道）才能提供的真实素材。这一步不是可选，是硬性 gate。

**品牌号场景的特殊性**：个人创作问作者的"个人经历"，因为第一人称就是作者本人。品牌号写作问的不是"你的经历"，而是**"你作为从业者看到的一线素材"**——客服反馈、用户群吐槽、同事观察、行业内幕，这些不需要你是主角。

#### 3.1 四维度提问（每篇写作前必问）

每个维度问一次，不强求每题都答出内容，拿到几条算几条。问法建议如下，可按实际情境调整措辞：

1. **真实场景 / 案例**
   > "这件事你有没有具体的用户故事、客服反馈、用户群里的吐槽、同事观察到的场景可以给我一两条？哪怕只是片段。"

2. **从业者内部视角**
   > "行业内部对这事实际是怎么看的？有没有外行人不知道、但懂行的人一看就懂的内幕、设计取舍、或者行业潜规则？"

3. **情绪点**
   > "用户在这个场景下最典型的情绪是什么（愤怒 / 焦虑 / 惊喜 / 困惑 / 委屈 / 吐槽欲）？你自己对这件事最有感触的点在哪？哪个细节让你兴奋、想吐槽或者心疼用户？"

4. **反差 / 钩子**
   > "有没有'大家以为 A，其实是 B'的反差可以埋？或者某个一上来就能抓住注意力的钩子？"

#### 3.2 按原型差异化门槛

不同文章原型对真实素材的依赖度不同，按下表判断是否达标：

| 原型 | 必须拿到的维度数 | 原因 |
|---|---|---|
| 故障排查 / 排雷避坑 / 产品体验 | **≥ 3/4** | 强依赖真实场景，编的场景一眼假 |
| 调查实验 / 现象解读 | **≥ 2/4** | 有数据或观察支撑即可 |
| 产品科普 | **≥ 1/4** | 知识型，逻辑清晰就行 |
| 自由 (`free`) | **0（不强制）** | 原型本身就跳过结构检查 |

#### 3.3 未达门槛时的行为（不报错，告知 + 让用户选）

**不要直接阻塞写作**。应明确告知用户当前素材状态，让他自己决策：

> 按 <原型> 原型，需要拿到至少 N 个维度的真实素材，现在只有 M 个（缺：<具体缺哪几个维度>）。
>
> 我现在可以直接开写，但 <具体会影响的部分，例如"场景描写需要 AI 自己想象，可能显得假"> 。
>
> 两个选项：
> A. **先补素材**（我可以再问你几个具体问题，例如"最近一周客服处理最多的是哪类问题？"）
> B. **继续写**（接受场景靠推理生成，可能不够真实）

用户明确选 B 后才开写；选 A 则继续追问，直到达标或用户主动停。

#### 3.4 第一人称真实感原则（子条：仍保留）

即使前 3 步都达标，**只要文章使用第一人称**，场景细节依然要再过一次这几条硬规则：

- **场景细节必须经得起推敲**：不确定的细节宁可用模糊描述（"忙得没人抬头"）也不要编造具体画面（❌"张经理一拍桌子"）
- **情绪反应要克制**：用具体行为代替情绪形容词，不写"震惊""说不出话"
- **信息引入方式要自然**：行业数据不能在第一人称视角里突然切换成科普语气，要通过对话、闲聊等叙事手段引入
- **对话内容要真实**：角色说的话应是那个人真实可能说出的，不是作者借角色的嘴表达观点

### 4. 根据风格源组织素材

- **用官方调性写**（`official`）→ 严格套用产品档案的「写作偏好」、「品牌规则」、「核心痛点库」
- **模仿博主写**（`mimic_blogger`）→ 加载博主风格报告；应用报告中的「推荐词组清单」「开篇方式」「节奏」；禁用报告中的「专属自称」
- **自由写**（`free`）→ 无预设风格，按题材自然写

### 5. 按原型展开

文章原型详见 references/article-archetypes.md。每种原型有自己的"写作重心"。

**若 `archetype == free`**：跳过 references/article-archetypes.md 的模板加载，只按主风格源 + borrowed + 主题组织结构（Step 6 的单文件结构仍适用）。

### 6. 产出单文件

**文件路径**：`$BRAND_WRITER_HOME/articles/<文章标题>/<文章标题>.md`

先 `mkdir -p` 这个目录（含 images/ 子目录，即使配图还没生成也先建）。

**单文件结构**：

```markdown
---
tags:
  - brand-writer/content/article
created: YYYY-MM-DD
product: <产品名，如 example-product>
style-source: 官方调性 / <博主名> / 自由
archetype: <原型名，如 故障排查>
---

# <文章标题>

## 标题候选
1. ...
5. ...（每个 25 字以内）

## 简介
（100 字以内，钩子优先，反差/悬念/痛点共鸣之一）

## 关键词
（5 个，逗号分隔）

## 封面图 Prompt

**必须**完整复制 `~/.claude/skills/brand-writer-image/references/cover-template.md` 的「固定 Prompt 模板」，**仅替换末尾 `Subject: ...` 部分**为本文核心关键词对应的场景描述（1-2 句英文，主体图标/物件 + 人物姿态/情绪）。

- 不要在本文件内重写或节选模板（避免与 cover-template.md 漂移，V2 已统一为单源）

- 写作时直接读 cover-template.md 取最新模板文本

## 正文

## English Version

5. ...

同上，复制 `cover-template.md` 的固定模板，Subject 按英文版文章内容重新构思（其他字段完全一致）。

### Body

```

> **注意（V2 变更，D2）**：正文 md **不再包含自检报告**。四层自检由 brand-writer-check 写入独立的 `self-check-report.md`，与正文同目录。

### 7. 更新 session + 自动 chain 到 brand-writer-check

1. 更新同目录 `_session.json`：`stage` 从 `drafting` → `self_check`，`updated_at` = 当前 ISO 时间
   - **stage 字段后续只改 drafting→self_check 这一次**。`self_check` → `human_review_pending` → `idle` 的状态转换全部由 brand-writer-check 负责，write-article 不碰。
2. 告知用户：

> ✅ 正文已保存到 `$BRAND_WRITER_HOME/articles/<名>/<名>.md`。
> 我会自动跑四层自检。自检通过后会停在"等人工审阅"状态，不会直接生成社媒/配图。

3. 直接进入 brand-writer-check 流程。**不要让用户另外触发。**

## 借鉴维度应用（V2 新增，D6）

当 `borrowed` 列表非空时，按维度覆盖主风格源对应部分：

- `title` → 5 个标题候选优先套借鉴博主的标题套路
- `opening` → 开篇钩子用借鉴博主的打开方式
- `pacing` → 叙事节奏按借鉴博主的段落密度/长度
- `ending` → 结尾方式用借鉴博主的
- `interaction` → 提问密度/共情策略用借鉴博主的

读取每条 borrowed 记录中 `report_path` 指向的风格报告，定位对应维度 section，应用其特征。写完后在「风格还原说明」里显式列出：主风格 + 各借鉴（博主/维度）。

## 配图位置标注（硬性要求）

下游 `brand-writer-image` 依赖正文中的 `📷 **配图建议**` 段落决定在哪生成几张图。**写正文时必须内联插入这些标注**，否则配图链路直接断掉。

### 密度规则

- 1500 字正文，插入 **3-4 张** 正文配图标注（封面不计入，封面 prompt 已在单独 section）
- 正文长度每增减 500 字，配图数量 +/- 1 张
- **禁止**：全文 0 张、首段前 1 张、末段后 1 张

### 插入位置

- **允许**：两段之间的过渡处、需要强化情绪/概念/场景的节点、长推理段落之后的"喘息点"
- **禁止**：开篇钩子段之前（破坏第一印象）、结尾收束段之后（破坏余味）、紧贴标题候选/简介/关键词 section
- **避免**：连续两段之间都插图（节奏破碎）

### 格式（精确匹配，不允许改写）

**单一事实来源**：`~/.claude/skills/brand-writer/references/constants.md` 的「配图标注格式」section。写作时必须完全按该格式输出——前缀 `📷 **配图建议**`、后缀 `（AI生成/设计师制作）`、全角冒号 `：`、30-50 字中文描述（主体+场景+情绪/构图，不写风格词/颜色词）。

**合格示例**：
```markdown
📷 **配图建议**（AI生成/设计师制作）：一个疲惫用户盯着手机屏幕上的 "登录失败" 红色提示，背景是错位的 AI 算法网格
```

**不合格示例**：
```markdown
📷 **配图建议**：配个图吧   ← 描述太空
📷 配图：用户登录失败     ← 格式不对（缺 "**配图建议**" 和 "（AI生成/设计师制作）"）
[此处配图]                  ← 完全不按格式
```

### 自检保障

`brand-writer-check` L1 会按正文字数动态判定配图密度（约每 500 字一张配图）。具体判定规则见 `brand-writer-check/SKILL.md` Layer C — 字数越多，期望的配图数越多；无需在写作时背死阈值。

**最低要求**：正文中至少出现 1 次 `📷 **配图建议**`（`0` 次 = L1 🔴 强禁不通过）。
